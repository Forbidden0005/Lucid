# Release Packaging

This document defines the current Lucid release path.

## Current decision

The first supported production release target is:

- unpackaged
- self-contained
- `win-x64`
- generated by `dotnet publish`

Current publish command:

```powershell
dotnet publish lucid-desktop\Lucid.App\Lucid.App.csproj `
  -c Release `
  -p:Platform=x64 `
  -r win-x64 `
  --self-contained true `
  -p:WindowsPackageType=None
```

## Why this is the current target

This repository currently has:

- `EnableMsixTooling=true`
- `WindowsPackageType=None`
- no active `lucid-desktop/Lucid.App/Package.appxmanifest`

That means an MSIX release path is not complete or honest to claim today. The unpackaged self-contained publish path is the current production-hardening baseline because it is:

- verifiable from the current repo
- compatible with the existing project file
- suitable for CI artifact generation
- lower risk than introducing packaging metadata, signing, and installer behavior without end-to-end validation

## Current CI artifact

The GitHub Actions workflow should publish and upload:

- `lucid-release-win-x64-unpackaged-package`

Artifact source folder:

- `lucid-desktop/Lucid.App/bin/x64/Release/net8.0-windows10.0.19041.0/win-x64/publish/`

Packaged distribution output:

- `release/packages/lucid-<version>-<channel>-win-x64-unpackaged-self-contained.zip`
- `release/packages/lucid-<version>-<channel>-win-x64-unpackaged-self-contained.zip.sha256`
- `release/packages/lucid-<version>-<channel>-win-x64-unpackaged-self-contained.update.json`
- `release/packages/feeds/index.json`
- `release/packages/feeds/<channel>.json`

Package layout:

- `app/` — the verified published application payload
- `installer/Install-Lucid.ps1`
- `installer/Uninstall-Lucid.ps1`
- `installer/Migrate-LucidData.ps1`
- `installer/Export-LucidSupportBundle.ps1`
- `docs/RELEASE-NOTES.md`
- `docs/SUPPORT-AND-CRASH-POLICY.md`

Artifact preparation now adds:

- `RELEASE-SHA256.txt`
- `release-artifact-manifest.json`
- `SMOKE-TEST-CHECKLIST.md`
- `release-smoke-result.json`

Those files are generated by `scripts/prepare-release-artifact.ps1` after publish locally and in CI.
They are then validated by `scripts/verify-release-artifact.ps1` before the artifact is treated as release-ready.
`scripts/run-release-smoke.ps1` executes the current launch smoke gate and records the result into the artifact.
`scripts/package-release-artifact.ps1` then produces the versioned distribution zip, and `scripts/verify-release-package.ps1` verifies the zip checksum and required entries.
`scripts/generate-release-update-manifest.ps1` generates the repo-side update descriptor for that package, and `scripts/verify-release-update-manifest.ps1` verifies it against the packaged zip.
`scripts/generate-release-update-feed.ps1` generates a publishable channel-discovery feed under `release/packages/feeds/`, and `scripts/verify-release-update-feed.ps1` verifies that the current release is discoverable through that feed.
`scripts/verify-installer-roundtrip.ps1` extracts that package into a workspace test root, runs install/uninstall, and verifies that the unpackaged installer path works without touching the real user profile.
`scripts/build-setup-exe.ps1` optionally wraps the verified zip in an Inno Setup shell. It derives the exact package filename from `release/release-metadata.json`; it does not select packages by timestamp. Run it directly or pass `-BuildSetupExe` to `scripts/verify-release.ps1` when `ISCC.exe` is installed.
`installer/Export-LucidSupportBundle.ps1` exports a support bundle from `%LocalAppData%\Lucid`, and `scripts/verify-support-bundle-export.ps1` verifies that export path against a workspace-scoped Lucid data root.
The packaged installer path now also verifies upgrade success, downgrade blocking by default, allowed downgrade behavior with `-AllowDowngrade`, and current-version rollover after uninstall.
`installer/Migrate-LucidData.ps1` now runs as part of install, normalizes known legacy root-level data files into their canonical subdirectories, creates a migration ledger under `%LocalAppData%\Lucid\Migrations`, and backs up any moved legacy files before mutation.

## Version source of truth

Lucid now has two repo-tracked release metadata artifacts that must stay in sync:

- `Directory.Build.props`
- `release/release-metadata.json`

Current policy:

- `Directory.Build.props` is the assembly stamping source for `Version`, `AssemblyVersion`, `FileVersion`, and `InformationalVersion`
- `release/release-metadata.json` is the release-governance source for channel, packaging, runtime, signing mode, and release notes location
- `scripts/validate-release-metadata.ps1` fails if those files drift
- local verification and CI both run that validation before release build/publish work

## Signing policy

Current signing status is intentionally explicit:

- CI artifacts are allowed to be `unsigned-ci-artifact`
- unsigned artifacts are valid for internal verification only
- external distribution requires signing before release

Current required policy before public or user-facing distribution:

- switch `release/release-metadata.json` to a signing mode that requires Authenticode signing
- define certificate source and operational ownership
- publish checksums with the release artifact
- verify signed artifact launch and SmartScreen behavior

Current signing operation path:

- `scripts/sign-release-artifact.ps1` is the operational signing entrypoint
- when `signingMode` is `unsigned-ci-artifact`, signing is skipped intentionally
- when `signingMode` is `authenticode-required`, the script requires:
  - `LUCID_SIGNING_CERT_PATH`
  - `LUCID_SIGNING_CERT_PASSWORD`
  - optional `LUCID_SIGNING_TIMESTAMP_URL`
- signing runs before the smoke gate, checksum generation, and artifact verification so the prepared artifact reflects the final signed bits

Current verification behavior:

- checksum and manifest integrity are enforced now for every prepared release artifact
- the release smoke gate now launches `Lucid.App.exe`, requires it to stay alive past the startup threshold, closes it, and records the result into `release-smoke-result.json`
- if `release/release-metadata.json` switches to `authenticode-required`, `scripts/verify-release-artifact.ps1` will require valid Authenticode signatures on `Lucid.App.exe` and `Lucid.App.dll`
- the versioned release zip is now built and verified before CI upload
- the unpackaged installer and uninstaller scripts are now round-trip verified against the packaged zip in a workspace-scoped install root
- a release update manifest is now generated and verified alongside the package
- a release update feed is now generated and verified alongside the package
- a support-bundle export path is now present and verified without touching the real user profile
- downgrade attempts are blocked by default, and installer multi-version behavior is now verified through the packaged release path
- installer-managed data migration is now explicit and verified through the packaged release path

Until that work is complete, CI artifacts are production-hardening artifacts, not final customer distribution artifacts.

## Release notes policy

Every version in `release/release-metadata.json` must point at a concrete notes file.

Current file:

- `docs/releases/0.1.0-preview.md`

Current smoke checklist:

- `docs/releases/smoke-test-checklist.md`

Current update publication contract:

- `docs/update-publication.md`

## Deferred work

MSIX is intentionally deferred until these items are designed and verified:

- `Package.appxmanifest`
- package identity and publisher configuration
- signing certificate strategy
- upgrade behavior
- installer and uninstall behavior
- update policy
- first-run validation

Until that work exists, the roadmap should treat MSIX as planned, not active.
